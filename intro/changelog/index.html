    Change Log

    This holds the change history for Bonfire as we lead up to a 1.0 release. It's not exhaustive, but should give you a good idea of the changes that have been made and how it might impact you.

    IMPORTANT! Breaking changes are marked with words breaking change in parentheses right after the date.

    6 November 2026

    A decimal field type. It takes places (default 2), min and step, renders a number input and saves a string such as "19.99", so a DECIMAL column never passes through a float. See Field types.

    Resources: a model in the admin as one class. Bonfire\Resources\Resource names a model, a URL slug, a permission prefix and the pages it has. service('resources')->register() in initAdmin() adds the sidebar item, and resource_routes() in Config/Routes.php declares the routes. A generic ResourceController renders the list: the columns, which leave out textarea and markdown fields unless columns() says otherwise, sorting, paging and htmx refresh, guarded by {permission}.list. Only the list page exists so far. A list.php beside the resource replaces the package's view. See Resources.

    Resources: search, filters, global search and the Recycler. A resource's $search columns give its list a search box and put its records in the admin's global search. Its filters(), in the shape of a model's $filters, show in the Filters cell's panel and narrow the list. Search, filters, sorting and paging combine, and survive htmx refreshes. register() also adds a soft-deleting model to the Recycler. The Filters view cell takes a resource slug beside a model. See Resources.

    6 November 2026 (breaking change)

    The field system moved from Content to Bonfire\Fields. Resources and actions will use the same fields as blueprints, so Field, FieldType, FieldTypes and the generic types (text, textarea, markdown, toggle, select, integer, date and datetime) now live in Bonfire\Fields, the types under Bonfire\Fields\Types. slug, terms and entries stay in Bonfire\Content\Fields. Blueprints work as before. There are no aliases, so a custom field type, or code of yours that names the old classes, breaks until you change these:

    • Namespace. Bonfire\Content\Field is Bonfire\Fields\Field, Bonfire\Content\Fields\FieldType is Bonfire\Fields\FieldType, Bonfire\Content\Fields\FieldTypes is Bonfire\Fields\FieldTypes, and Bonfire\Content\Fields\ChoiceList is Bonfire\Fields\ChoiceList. A type that extends one of the built-in types, such as TextField, now finds it in Bonfire\Fields\Types. check() throws a Bonfire\Fields\FieldException, not a ContentException.
    • Two renamed methods. toFrontMatter() is toStored() and fromFrontMatter() is fromStored(), with the same arguments. ChoiceList::fromFrontMatter() is ChoiceList::fromStored(). key() and storedInFrontMatter() are no longer on FieldType: a type that overrides them implements Bonfire\Content\Fields\ContentFieldType instead.
    • The config key. Config\Content::$fieldTypes is gone. Register your types in $types of app/Config/Fields.php, which extends Bonfire\Fields\Config\Fields. The language strings Content.selectInvalid, Content.integerInvalid, Content.integerMin and Content.integerMax are Fields.* now.
    • The view path. Overrides of an input move from app/Views/content/fields/<type>.php to app/Views/fields/<type>.php, and now apply wherever a form uses fields. Copies in the old folder are ignored. The @var of the partials is Bonfire\Fields\Field.

    The form behind an entry's fields is Bonfire\Fields\Form, and its view is Bonfire\Fields\Views\form_fields rather than Bonfire\Content\Views\form_fields. See Custom field types.

    Content: blueprint sections. A blueprint can group its fields with sections: instead of fields:. Each section has a title, optional instructions and columns (1 to 3), and its own fields:. A field can set width: full, and markdown and textarea fields span the row by default. Storage stays flat, so a sectioned blueprint saves the same front matter as the same fields in one list. See Sections. If you copied entry_form.php, global_form.php or term_form.php from Bonfire\Content\Views into your app, they break: the controllers now give them $sections rather than $rows, which they pass to Bonfire\Fields\Views\form_fields as ['sections' => $sections]. That view still takes rows for a form with no sections. Bonfire\Fields\Form has a sections() method for other callers, and a custom field type can override isFullWidth().

    Content: components in Markdown, and content_markdown(). $entry->content() now converts the Markdown, then expands any <x-…> View Components in it, so it works in controllers and feeds and not only when echoed in a view. A body with an <x-…> tag now gets that component's HTML in content(), and a tag for a component that doesn't exist throws a RuntimeException naming it, outside production. In production it's logged and the tag is removed. Pass content(components: false) for the old, Markdown-only output. The new content_markdown($markdown) helper renders any Markdown string the same way, for front matter and block fields. It isn't called markdown() because Postal already defines that. See Markdown and components.

    viewMeta escapes attribute values. render() now runs every value of an addMeta(), addLink(), addScript() and addStyle() entry through htmlspecialchars(), so a " or & can no longer break out of a tag. If you escaped a value yourself before passing it in, it is now escaped twice, so pass the plain value. Titles and the content of raw scripts are unchanged. content_seo() was updated to match. See View metadata.

    6 November 2026

    Fields: belongsTo. A new belongsTo field type picks one record of another model. Give it a model class and a title column, and the form shows a dropdown of the records' titles and saves the chosen ID. A save is refused if the ID isn't a record of the model, and a blueprint whose model or title can't be found is refused. See Field types.

    Content: blocks. A new blocks field type holds a list of typed blocks in an entry's front matter, such as a hero or a call to action. Block types are files in resources/blueprints/blocks, with a title, an optional icon and fields. $entry->blocks($field) returns a list you can loop over, filter with ofType() and render, $entry->block($field) is the first block, and $entry->renderBlocks($field) renders them in order through app/Views/blocks/<type>.php. A block's field() is cast by its blueprint, as globals() does. A missing partial throws outside production and is logged in production. max_items and min_items are enforced on save, with errors keyed by position. The admin lists the blocks and keeps them on save, but you write them in the entry's file. New Config\Content::$blockViewPath and FieldType::itemErrors(). See Blocks.

    View metadata: no duplicates, and raw styles. An identical addMeta(), addLink(), addScript() or addStyle() entry, or identical raw script, is output once, so block partials can each declare the assets they need. New addRawStyle() and rawStyles() add a <style> block, and the App theme's layout prints it. If you keep your own copy of that layout, add <?= $viewMeta->render('rawStyles') ?> to the <head>. The docs also show how to give one page its own assets. See View metadata.

    Content: reorganized docs. The Content pages are grouped by task in the nav. Reindexing and deploys have their own page, The index and deploys, and feeds and the sitemap moved out of Routing to Feeds and sitemaps. Configuration and commands lists every Config\Content property and content:* command. php spark bf:agents now points agents at the Content docs too, so run it again to update your AGENTS.md.

    Docs: nested sections collapse in the side nav. The admin's Docs pages show a nested section of mkdocs.yml, like Content's "Modeling content", as a collapsible group in the side nav. It opens when it holds the current page.

    5 November 2026 (breaking change)

    The Recycler handles non-integer keys. So that it can list resources with UUIDs, CustomRecyclerRestore::recyclerRestore() and CustomRecyclerPurge::recyclerPurge() now take int|string $id, as do RecyclableResource::restore(), purge() and RecycleController::restore() and purge(). A model of yours that implements either interface with int $id is a PHP fatal error when the class loads, so change its signature to int|string $id. The key arrives from the URL as a string, and the routes now take (:segment). See The Recycler.

    Recycler restore and purge are POST only. They changed data on a GET request, so a forged link or image could make a logged-in user restore or purge a record. recycler-restore and recycler-purge are now POST routes that always check the CSRF token, even if your app doesn't turn the filter on globally, and the list uses forms. If you link to these URLs, or have your own copy of listResource.php, change the links to forms with csrf_field(). A GET to either URL now gives a 404. See The Recycler.

    5 November 2026

    Content: scaffolding. php spark content:scaffold <collection> writes starting index and show views for a collection into app/Views/<collection>/, built from its blueprints' fields. The index view uses the pagination recipe and the show view calls content_seo(). --controller also writes a controller for the collection to hand off to. It never overwrites a file, says which ones it skipped, and prints the config line and the index route to add. See Scaffolding.

    Content: $entry->isPublished(). It says whether an entry has the published status and its published_at has passed, the same rule as published(), so you can check the entries an entries field links to, which include drafts. See Entries.

    Content: SEO values. $entry->seo() returns an entry's title, description, canonical URL and Open Graph values. A blueprint's seo key maps the fields that feed the title and description, which default to title and the body's first paragraph. content_seo($entry) adds them to the page's <head> through viewMeta, escaped. Config\Content::$autoSeo, off by default, does it for pages rendered from a collection's template. The App theme's master.php now also renders the link tags, which the canonical link needs: add <?= $viewMeta->render('link') ?> to a copy of your own. See SEO.

    Content: redirects. When an entry's URI changes, because you moved a page in the tree editor or a reindex found a renamed file, a moved page or a changed route, its old URI now answers with a 301 to the new one, and so do the old URIs of the pages below it. They're kept in content/redirects.yaml, which you should commit with your content, and not in the index, so content:reindex --fresh keeps them. A published entry at a URI always wins over a redirect from it, a trashed or unpublished entry gets none, and a chain of moves ends at the latest URI. Routes of your own can use content()->redirectFor($uri); findByUri() still treats an old URI as missing. This replaces the "no redirects" limit noted for pages. See Redirects.

    Content: front-end search. content()->search($term) returns a query on the published entries of every collection that have the term in their title or body, and content()->search($term, 'blog') narrows it to one collection. It works with paginate() and pager(), and Bonfire adds no search page, so build your own. See Searching.

    Content: sitemap. content()->sitemap() returns a response with a sitemap of every collection's published entries, which you can serve from any route of your own. Entries with no URI are left out. Set $sitemap = true in app/Config/Content.php to have Bonfire serve it at /sitemap.xml. It's off by default, and your own routes win over it.

    Content: editing globals in the admin. Each set of globals that has a blueprint gets an item in the Content menu and a form built from the blueprint, with the same field types and validation as entries. It needs content.access and content.edit. A save writes the YAML file whole and is refused if the file changed since the form loaded, like an entry. See Globals.

    Content: draft preview. An entry's form has a Preview button for users with content.edit. It gives a signed link, good for 24 hours, that shows the entry through the collection's template or controller whatever its status, to anyone who has the link and with no login, so a client can review a draft. The response is noindex and never cached, and a collection with neither a template nor a controller has no preview. Links are signed with the app's encryption key. See Previewing a draft.

    Content: page caching. A collection with cache: 3600 in its config has its routed pages served to guests from the cache for that many seconds. It's off unless a collection sets it. Only GET requests with no query string from guests that the fallback route serves with a 200 are cached. Saving, trashing, restoring or purging an entry, moving pages in the structure, saving a term or menu, and any reindex (including content:reindex) clear all of Content's cached pages. See Caching.

    Content: globals. Keep site-wide values in content/globals/<handle>.yaml, describe them with a blueprint at resources/blueprints/globals/<handle>.yaml, and read them anywhere with globals('site')->field('name', 'default'). The value is cast by the blueprint's field type, and a missing one gives the default. Globals are read from the file, with no index or migration, work with auto-routing off, and have no routes. See Globals.

    Content: collection feeds. content()->feed('blog') returns a response with a collection's published entries as an RSS 2.0 feed, to return from a route of your own. An optional /feed/{collection} route is behind $feedRoute in app/Config/Content.php, off by default, and your routes win over it. See Feeds.

    Content: collection index pages. Listing a collection shows a route and view of your own that list a collection's published entries a page at a time, with pager links from $query->pager()->links(). Bonfire adds no index route, and paginate() still returns a plain list.

    Content: structure editor save bar. Moving a page on the Edit structure screen now shows the save bar. Before, the bar stayed hidden, so with JavaScript on there was no way to save a new order. Discard opens the page again, which puts the pages back.

    Content: admin search. The admin search box now finds entries. It matches the term in an entry's title or Markdown body, skips trashed entries, and shows nothing to users without content.access. Results show the title, collection and status, and link to the edit form for users with content.edit. See Editing entries in the admin.

    Documentation in the admin. Outside production, the sidebar has a Documentation group that shows this guide for the version you have installed, with its structure read from mkdocs.yml. Anyone with admin.access can read it, and production has no menu and answers with a 404. See Documentation.

    Wider documentation nav. On wider screens the page list beside the documentation grows to fit most titles, and a title that still wraps no longer runs into the next one. Pages also read more easily, with larger body text, smaller headings and shorter lines.

    Check your Debug Toolbar config. If your app's app/Config/Toolbar.php has no $disableOnHeaders property, htmx requests such as the Content preview fail after the first one in development. See If htmx stops working in development.

    Content: delete to trash. Users with content.delete can delete an entry from the list or its form, which moves its file to content/.trash/<collection>/ and takes it off the site. Content entries in the Recycler restores or purges it, with recycler.view. Deleting a page takes the pages below it, after a confirmation that says how many, and restoring brings them back in their exact place in the tree. A trashed entry keeps its slug and URI, and an entries link to it survives a save and works again after a restore. content:reindex goes by where the file is, so a trashed entry stays trashed after --fresh. You probably want content/.trash/ in your .gitignore, and a fresh clone followed by a reindex then loses that machine's Recycler contents. See Deleting and restoring.

    Content: navigation menus. Add a config at content/navigation/<handle>.yaml and users with content.structure get an editor under Content in the sidebar, to build a menu from entries and typed-in links. The items live in content/trees/navigation/<handle>.yaml. navigation('main') returns them as a tree with title, url, active and children, and leaves out an item, and those below it, when its entry isn't live. An item that links to an entry takes its URL from the entry, so renaming a slug changes the menu by itself. The App theme has a sample partial at themes/App/_navigation.php, which a theme you already published needs to copy. See Navigation menus.

    The Recycler's resource chooser works again. Picking another resource in the dropdown on Tools → Recycler did nothing. It now swaps the list in place with htmx and starts on the first page of the chosen resource.

    Lithuanian translations completed. Content.php and Docs.php now have Lithuanian files, and the remaining keys were added to Bonfire.php, Email.php, Tools.php, Users.php and Widgets.php: the dashboard editor, Mail Previews and Outbox, the mailer list, the log viewer and system health, and the users and chart widget settings.

    4 November 2026

    Content: getting started and constraints. Getting started walks you from a fresh install to a published blog post. Content now explains the file-first model and when to run php spark content:reindex, which belongs in your deploy. Constraints and known gaps lists what Content doesn't do yet: it needs the content directory on one server or shared storage, it doesn't redirect old URIs, it drops YAML comments when the admin saves, it doesn't use git, and it has no per-collection permissions.

    Content: pages and structures. Give a collection structure: true (and optionally max_depth) and its entries form a tree, kept in content/trees/collections/<handle>.yaml. The reindex gives each entry a parent_id, a sort and a URI built from its parents, such as /about/team, which the front-end route serves. Renaming a page or moving it updates the URIs below it. There are no redirects for the old URIs in this version. Users with content.structure get an Edit structure screen with drag and drop, which refuses a tree deeper than max_depth or one that changed on disk since it was opened. New entries go last at the root, and entries the tree file doesn't name are indexed there too. See Pages and structures.

    Content: taxonomies and terms. Tags, categories and other taxonomies are now files. A taxonomy has a config at content/taxonomies/<handle>.yaml, and each term is a YAML file in content/taxonomies/<handle>/. A collection opts in with taxonomies: [tags], and keeps an entry's terms as slugs in its front matter (tags: [php]). A new terms blueprint field type tags entries from the admin. php spark content:reindex now fills the content_terms and content_entry_terms tables from the files, and content()->collection('blog')->whereTerm('tags', 'php') finds the published entries with a term. content()->terms('tags') lists the terms with their number of published entries. Terms have a list, a form to create them and a form to edit them in the admin, which need the content.structure permission, and with $autoRoute on a taxonomy can serve a page for each term from a route and a template. Nothing changes for a site that has no taxonomies. See Taxonomies.

    Content: more field types, and your own. Blueprints can use select (one option, or several with multiple: true), integer, datetime and entries, which links to entries of the collections you name. Read the links with $entry->entries('related'), which skips a target that has since been deleted or trashed, or look entries up with content()->findMany($ids). Register a field type of your own in $fieldTypes in app/Config/Content.php. See Field types and Custom field types.

    Content: edit entries in the admin. Content in the sidebar has an item for each collection, with a list of its entries and a form to create and edit them. The form is built from the collection's blueprint in resources/blueprints/collections/<collection>/<blueprint>.yaml, with text, textarea, markdown, slug, toggle and date fields. Saving checks the input, writes the entry's Markdown file in one step and updates the index. It refuses to save if the file changed on disk since the form was opened. Comments in an entry's front matter don't survive a save. Publishing, and setting published_at, need their own permission. Nothing changes for a site that has no collections. See Editing entries, Blueprints and Field types.

    There are five new permissions: content.access, content.edit, content.publish, content.delete and content.structure. The last two are held back for later and nothing uses them yet. If you published your own AuthGroups, add them there, or run php spark bonfire:permissions, which declares them and grants content.* to superadmin and admin. Until you do, Content stays hidden from those groups.

    3 November 2026 (breaking change)

    php spark bf:install no longer overwrites theme files you already have. Running it again used to copy Bonfire's themes over themes/, discarding your edits to Admin, App and Auth. It now copies only the files that are missing and says how many it left alone. To replace your files with Bonfire's anyway, run php spark bf:install -f; that also discards your changes, so commit them first. If you counted on a second run to refresh the themes after an update, add -f or merge the files by hand.

    php spark bf:install says when it could not make a change. It edits .env, app/Config/*.php and composer.json by looking for the text the framework ships. When that text is not there, for example after a CodeIgniter update, the installer used to skip the edit and still report success. It now names each file it could not update, what it looked for, and exits with an error. Config files it cannot copy correctly are not written. The SQLite3 option for app/Config/Database.php was one of these edits that did nothing on CodeIgniter 4.7. Running the installer again no longer adds app.indexPage or the SQLite3 .env lines a second time, keeps an existing encryption key, and keeps the final newline in .env.

    3 November 2026

    Asset URLs are built and read by one class. asset() and the /assets/... route now share AssetLocator, so the URL format can't drift between them. The URLs themselves are unchanged. asset() now marks a path in an unknown folder as a missing asset instead of raising a PHP warning, the route refuses .. segments, and asset_link() escapes the URL and any attributes you pass it.

    Content: serve entries on your front end. Set $autoRoute = true in app/Config/Content.php, give a collection a route, and a template or a controller, and run php spark content:reindex. Your routes always win, and only published entries are served. content()->findByUri() does the same lookup for routes of your own, and $entry->content() renders the Markdown. Nothing changes unless you turn this on. See Routing.

    Content: read file-based content from your code. Keep entries as Markdown with YAML front matter under content/, index them with php spark content:reindex, and query them with content()->collection('blog')->published()->paginate(). Run php spark migrate --all to create the index tables. Nothing changes until you do this: there's no admin screen or routing yet. See Content.

    One Mailable file that can't be loaded no longer breaks Mail Previews. A parse error or a missing parent class in a file in a Mails folder used to give a 500 on Tools → Mail Previews and on every preview and send. The list now shows that Mailable with its error, its preview page shows the same error, and the others work as before.

    Mail Previews' Send to me no longer claims a discarded or logged mail was sent. Sending through the null mailer now says the message was discarded, and through log that it was written to the log, the same as the test send in Settings → Email. A failover chain is judged by its first mailer.

    2 November 2026 (breaking change)

    Mail Previews' Send to me drops more recipient headers. Resent-* headers and Disposition-Notification-To are removed from the preview, so sendmail can't deliver it, or a read receipt, to anyone but you. Reply-To is kept.

    Mail Previews' Send to me refuses a looping failover chain and hides secrets in errors. A chain that loops now shows an error and sends nothing, where before it crashed PHP. A failed send shows the error with the mailer's known secrets, and those of its failover children, removed, the same as the test send in Settings → Email.

    Branded Markdown activation and two-factor emails. New installs send them with your site name and accent color, and a plain text part. This doesn't change your emails when you update: your published app/Config/Auth.php keeps its HTML views until you add action_email_activate_markdown and action_email_2fa_markdown to $views. An app that never published Auth.php does switch on update. The magic link email stays as it is. See Your email templates.

    Settings → Email no longer edits mail transports. The protocol, SMTP and sendmail fields are gone: mail is configured in app/Config/Mailer.php and .env. The page now lists every mailer with its transport and settings, marks the default, links failover chains to their mailers, and shows secrets only as Set or Empty. It warns while the legacy bridge is active, while old transport rows are still in the settings table, and when the default mailer discards mail or isn't defined. You can still edit the From name and address, and a new Test send mails a fixed message to an address you type, through a mailer you choose. Installs on the bridge keep sending as before, but change these settings in .env or app/Config/Email.php, or move to Mailer.php with php spark bonfire:email-env. See Email Settings.

    Tools → Mail Previews shows your Mailables in the admin, in every environment: the HTML, plain text and raw MIME of each one, and a Send to me button that mails it to your own address through a mailer you choose. It needs the new email.preview permission. You publish your own AuthGroups, so run php spark bonfire:permissions, which grants email.* to superadmin and email.preview to admin. Until you do, the screen stays hidden. See Mail Previews.

    Tools → Mail Outbox logs every email your site sends and every send that fails: the addresses, subject, status, error, attachment names and the Mailable that built it, never the message body, because magic link and password reset emails carry live login tokens. Filter it by status, mailer, recipient and date. Settings → Email has a new Days to keep (Email.logRetentionDays, 30 to start with); 0 turns the log off. php spark email:prune deletes older rows, and about one send in a hundred prunes too. The Outbox needs the new email.log permission, granted to superadmin only. Run php spark migrate --all to create the email_log table, and php spark bonfire:permissions to grant the permission. Until you do, the screen stays hidden, and a missing table never stops an email from sending. Every row is logged under the default mailer, because Postal doesn't tell listeners which named mailer sent a message. See Mail Outbox.

    Two new dashboard stat cards, Mail sent, last 7 days and Mail failed, last 7 days, come from the Outbox. The failed card turns red while its count is above zero and links to the Outbox filtered to failures. They need email.log and are hidden while Days to keep is 0. A stat card can now turn red while its value is above zero with the new highlightNonZero key, and take its value from a closure with addValueUsing(). See Mail Outbox.

    Mail keeps working after this update, and you don't have to do anything. Without an app/Config/Mailer.php, Bonfire now makes a deprecated legacy mailer the default. It sends through the transport your setting('Email.*') values describe, read at send time, so a Mailable no longer lands in Postal's null mailer, which discards it.

    The breaking part: if your app sends Postal Mailables and has no app/Config/Mailer.php, those messages used to be discarded and now really go out, through PHP's mail() if nothing is configured. If your app calls $this->validate('users'), add the rules you need to your own app/Config/Validation.php as public array $users. If you already declare $users there, Bonfire no longer merges its email, username, first_name and last_name rules into it, so add any of those you rely on.

    Fixes: Bonfire found no themes under CodeIgniter 4.7.5, so every admin and auth page failed with "Admin is not a valid theme folder". Theme::available() now lists theme folders itself instead of using get_dir_file_info(), which no longer returns folders.

    8 October 2026 (breaking change)

    The Recycler no longer guesses at what a model can do by checking method_exists(). A model that customizes the Recycler must now implement the matching interface from Bonfire\Recycler\Interfaces: CustomRecyclerQuery (setupRecycler(): Model), CustomRecyclerRestore (recyclerRestore(int $id): bool) and CustomRecyclerPurge (recyclerPurge(int $id): bool). Methods with those names on a model that does not implement the interface are no longer called. Without a custom hook, the Recycler now uses the model's own primary key and soft delete field instead of assuming id and deleted_at, and refuses to restore or purge a record that is not in the Recycler.

    Modules now register their recyclable resources with service('recycler')->register() from initAdmin(), instead of editing Config\Recycler::$resources. The Users module registers users this way, so $resources is empty by default; entries you already have in your own Config\Recycler keep working and take precedence over a module's. If you publish the Recycler listResource view, it now receives RecyclableResource objects as $resources and $currentResource (use ->label(), ->columns(), ->localizedColumns(), ->alias()) and no longer receives $currentAlias.

    The logs in the Tools area are now read and deleted through Bonfire\Tools\Libraries\LogStore, which only accepts file names like log-2024-01-31. Logs::getAdjacentLogFiles() moved to LogStore::neighbours() and Logs::paginateLogs() takes the page as its third argument instead of reading $_GET. If you publish the logs list view, each log now has a name (without extension) instead of a filename.

    Fixes: viewing and deleting logs now requires the logs.view and logs.manage permissions; before, any user with admin.access could read and delete the logs by calling the URLs directly. "Delete all" now removes only the log files. The levels count in the logs list counts entries instead of every occurrence of a level's name in a message.

    View Components now render self-closing (<x-foo />) and paired (<x-foo>…</x-foo>) tags through the same code, so the two forms no longer differ by accident. Two behaviours change:

    • A self-closing tag now passes its attributes to a component class, as the docs always said. Before, <x-foo attr="bar" /> lost attr whenever a FooComponent class existed, so the class' $this->data was empty. If your class worked around that, it now receives the attributes.
    • A tag whose view can't be found now always throws a RuntimeException (View not found for component: foo). Before, a paired tag with a missing view (or any error while rendering one) was swallowed and the raw <x-foo> tag stayed in the page. A regex failure while rendering components also throws now, instead of returning a number as the page.

    What a component view sees (the attributes as variables, $slot), the lookup order (theme first, then componentsLookupPaths) and the Components/<name>.php + <Name>Component.php convention are unchanged.

    8 October 2026 (breaking change)

    Everything about whether a dashboard widget is enabled, and what its display options are, now has one owner in Bonfire\Widgets: ItemSettings (the enabled flag of an item), DashboardContext (are we on the dashboard, and does this item show) and WidgetOptions (the options of the Stats widget and of each chart type). The settings keys stored in your database are unchanged.

    If you publish your own copy of the dashboard cell views (Cells/stats.php, Cells/charts.php, Cells/scripts.php) or the widgets settings.php view, note that they no longer receive $manager from Manager::manager(), which has been replaced by Manager::items(). Ask each item for $item->settings()->enabled() instead.

    Widget items now also report an item's settings through settings(), which is part of the Item interface. If you wrote your own item class implementing Bonfire\Widgets\Interfaces\Item, add settings(): ItemSettings to it. The protected $dashboardRoute property of StatsItem and ChartsItem is gone. StatsItem::addValue(), addValueByFreeQuery() and ChartsItem::addDataset() still only run their query on the dashboard when the item is enabled, and the check can now be swapped in tests through service('dashboardContext').

    Items in a second collection of a widget now show up on the widgets settings page and on the dashboard.

    8 October 2026

    The rules for who may edit, ban, delete or assign groups and permissions to whom in the Users admin now live in one place (Bonfire\Users\Libraries\UserAccess), and the views and the controller both use it. If you have published your own copy of the Users views form.php, permissions.php or _table.php, they now receive an $access variable (a UserAccess instance) instead of working out these rules themselves. Avatar storage moved to AvatarStorage.

    Fixes: purging several users at once now removes the avatar and meta info of every purged user, not only the first. A user with users.edit but without me.edit can no longer ban themselves.

    18 March 2025 (breaking change)

    The way widgets are enabled has changed in the database, so if you had widgets enabled before, they will all be disabled. To clear the database of the orphaned data about enabled widgets run this in your DB:

    DELETE FROM `settings`
WHERE `class` = 'Bonfire\Widgets\Config\Stats' AND `key` LIKE 'Stats_%';
DELETE FROM `settings`
WHERE `class` = 'Bonfire\Widgets\Config\Stats' AND `key` LIKE 'Charts_%';

    26 February 2025 (breaking change)

    Finished implementation of <x-button> component in the Admin theme. Users need to update the Admin theme (updated the component definition).

    19 January 2025

    Resource Meta Info (if you have configured such) can now be included in the Admin area search (see docs page Search for details).

    18 January 2025 (breaking change)

    Possibility to have Second Factor Authentication is added to Bonfire2, implementing Codeigniter Shield feature.

    To use the feature on existing installs you will first need to update the userspace Config file app/Config/Auth.php, in particular – the property $views, two keys relating to 2FA to look like this:

        'action_email_2fa'        => '\Bonfire\Views\Auth\email_2fa_show',
    'action_email_2fa_verify' => '\Bonfire\Views\Auth\email_2fa_verify',

    Failing to do that and enabling 2FA in the admin area will lock the users out of your website.

    To fix it, after modifying the config file, issue this command on your database to clean up references to wrong classes:

    DELETE FROM settings WHERE class="Config\Auth" AND key="actions";

    16 January 2025

    Bonfire can henceforth warn you about breaking changes (like need to update Admin/Auth themes, change config files, etc).

    To get such notifications when updating Bonfire, you can add a command to your composer.json scripts section:

        "scripts": {
        "post-update-cmd": [
            "php spark notify:breaking-changes"
        ]
    }

    New Bonfire install will automatically include this command.

    18 March 2024 (breaking change)

    <x-button> and <x-button-container> view components implemented.

    When updating, copy files themes/Admin/Components/button-container.php and themes/Admin/Components/button.php into the corresponding folder of your project's Admin theme. See #434 for details about the change.
